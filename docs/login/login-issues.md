## 2. 要決定事項（製造前に回答がほしいもの）

### L-01 認証方式を Spring Security にしてよいか

- 現状: `pom.xml` に認証関連の依存がない。全 URL が無認証で開ける。
- 提案: Spring Security 6 のフォームログイン＋サーバセッション方式（設計書 3.1）。
- 影響: 依存を追加した時点で全 URL が保護され、既存の POST / DELETE が 403 になる（L-04）。
- 決めること: この方式でよいか。
- **決定（2026-10-03）: Spring Security を必ず使う。**

### L-02 `users` の既存データの扱い

- 現状: `users` テーブルは存在するが、**中身は確認していない**（個人情報を含むため、調査時の行データ参照は見送った）。
- 懸念: 既存行の `password_hash` が BCrypt 形式でない場合、その利用者はログインできない。
- 確認してほしいこと: 次の SQL の結果。

  ```sql
  select count(*) as 件数,
         count(*) filter (where password_hash like '$2%') as bcrypt件数
  from users;
  ```

- 対応案:
  - 0 件 → L-03 の初期ユーザ登録だけで足りる
  - テストデータのみ → 削除して作り直す
  - 残したいデータがあり BCrypt でない → パスワードを再設定する手順が必要

### L-03 初期ユーザの登録方法

- 現状: サインアップ画面がなく（L-10）、ユーザを作る手段がない。
- 提案: 起動時に `users` が 0 件なら環境変数の値で 1 件登録する（設計書 5.4）。
- 代替案: BCrypt ハッシュを手で生成し、`db/migration` の SQL で INSERT する。
  ハッシュをリポジトリに置くことになるため推奨しない。
- 決めること: 提案の方式でよいか。2 人目以降の登録をどうするか（当面は DB へ直接登録か、L-10 を前倒しするか）。

### L-17 パッケージ名とテンプレートファイル名

- パッケージ: 認証は銘柄機能ではないため `org.example.web.auth` を提案する。
  `CLAUDE.md` の「機能は `web.stock.<feature>`」という構成に合わせて `web.stock.login` にする案もある
  （`settings` は `web.stock.settings` にある）。
- テンプレート: 既存の命名は機能名ベース（`settings/settings.html`）。
  `login/chasing_cats.html` のままにするか、`login/login.html` に改名するか。
  設計書は現在のファイル名のままで書いている。

### L-19 セッションタイムアウト時間

- 提案: 30 分（Spring Boot の既定値と同じ）。
- 銘柄詳細画面でパラメータを長時間調整する使い方がある場合は、延長を検討する。
  タイムアウト後の Ajax は 401 になりログイン画面へ遷移するため、入力途中の値は失われる。

## 3. 現在のソースにある問題

### L-04 既存 Ajax / fetch が CSRF トークンを送っていない

- 該当: `country.js`、`currency.js`、`industry.js`、`valuation-model.js`、`stock-list.js`、
  `stock-detail_002.js`、`settings.js` の計 16 箇所（うち POST / DELETE が 14 箇所）。
- 影響: Spring Security 導入後、登録・更新・削除・バッチ手動実行がすべて 403 になる。
- 対応案: 共通の `static/js/csrf.js` で jQuery と fetch の両方にヘッダーを自動付与する（設計書 7.1）。
  CSRF を無効化する方法は、セッション Cookie 認証と組み合わせると危険なため採らない。
- 補足: セッション切れ時に REST が 302 を返すと Ajax がログイン画面の HTML を受け取って誤動作する。
  REST は 401 を返し、JS 側で遷移させる（設計書 4.3）。

### L-05 ログアウトボタンが動かない／モック

- 各画面のヘッダーの `<button class="btn-logout">` には処理が付いていない（6 テンプレート）。
- 設定画面の `#btn-logout-settings` は `/top` へ遷移するだけ（`settings.js:146-151`）。
- `settings.test.js:88-99` が「`/top` へ遷移すること」を検証しているため、実装を変えるとテストが落ちる。
- 対応案: `POST /logout` のフォーム送信に統一し、テストを書き換える（設計書 5.2）。

### L-06 共通ヘッダーがなく、ユーザ名が固定文字列

- `<nav class="navbar">` が 6 テンプレートにコピーされ、ユーザ名は「テスト太郎 様」固定。
- 該当: `stock-list.html:27`、`country-list.html:28`、`currency-list.html:28`、
  `industry-list.html:28`、`valuation-model-list.html:28`、`settings.html:29`。
- `stock-detail002.html` にはナビゲーション自体がなく、銘柄詳細からログアウトできない。
- 対応案: `templates/fragments/header.html` に集約する（設計書 6.4）。
  CSRF 用の `<meta>` も全テンプレートに必要なため、同じフラグメントで配る。
- 決めること: 銘柄詳細画面にもナビゲーションを付けるか（画面デザインが他と異なり Tailwind を使っている）。

### L-07 メールアドレスの大文字・小文字の扱い

- `users_email_key` は大文字・小文字を区別する UNIQUE 制約である。
  `Taro@example.com` と `taro@example.com` が別ユーザとして登録できてしまう。
- 対応案: 登録時・検索時ともに小文字へそろえる。検索 SQL は `lower(email)` で比較する。
  件数が増えたら `lower(email)` の UNIQUE インデックスを追加する。

### L-08 `UserDao.selectById` の引数型が Entity と不一致

- `UserDao.java:17` は `selectById(Long id)`、`UserEntity.id` は `Integer`、DB は `integer`。
- 現在は未使用のため実害はない。`selectByEmail` を追加する際に `Integer` へ直す。
- `UserSimulationDao.selectById` も同じ不一致がある。

### L-09 通信が HTTP、DB パスワードが平文

- ローカルは `http://localhost:8080` で動いている。このままサーバへ置くとパスワードが平文で流れる。
- `application.properties:3` に DB パスワードが平文で入っている（`CLAUDE.md` の既知の課題）。
- `logging.level.org.springframework.jdbc=DEBUG` と Doma の DEBUG ログが有効で、
  SQL のバインド値（メールアドレス、パスワードハッシュ）がログに出る可能性がある。
- 対応案:
  - ローカル以外で動かす場合は HTTPS を前提にし、Cookie の `Secure` を有効にする
  - 初期ユーザのパスワードは環境変数で渡し、設定ファイルに書かない
  - `users` を扱う SQL のログ出力内容を製造時に確認する

### L-21 `CLAUDE.md` の記載が実態と合っていない

- 「Java のユニットテストは現状存在しない」とあるが、`src/test/java` に 28 ファイルある。
- JS テストの場所が `src/test/javascript/**` と書かれているが、実際は `src/test/resources/static/js/`。
- 対応案: ログイン機能の製造完了時に、認証の説明の追加とあわせて修正する。

### L-22 `users` 系テーブルの DDL がリポジトリにない

- `db/migration` は V001〜V005 のみで、`users`、`user_simulations`、`user_valuation_parameters` の
  CREATE 文が含まれていない。別の環境で DB を作り直せない。
- `user_valuation_parameters` は DB には存在するが、対応する Entity / DAO がソースにない。
- 対応案: 現在の定義を `db/migration` に書き起こす。第 1 フェーズでは `users` だけでもよい。

## 4. 第 1 フェーズで対応する課題

### L-18 バッチ専用起動時に初期ユーザ登録を動かさない

- 将来 `MarketDataBatchApplication`（非 Web 起動）を実装したとき、
  `InitialUserRegistrar` がバッチ起動でも走ってしまう。
- 対応案: `@ConditionalOnWebApplication` を付ける。

### L-20 ログイン画面のアニメーションの端末対応

- `mousemove` のみ対応（`chasing_cats.html:194`）。タッチ端末では猫が追いかけてこない。
- `body` が `overflow: hidden`（`:19`）のため、画面の高さが足りない端末や
  ソフトウェアキーボード表示時にログインボタンまでスクロールできない可能性がある。
- 「動きを減らす」設定（`prefers-reduced-motion`）を見ていない。
- 対応案: `touchmove` の追加、`overflow` の見直し、`prefers-reduced-motion` 時は猫を静止させる。
  スマートフォン対応が不要なら `overflow` の確認だけでよい。

### L-23 エラー画面（403 / 404 / 500）がない

- `@ControllerAdvice` も `templates/error/` もなく、Spring Boot の既定のエラー画面が出る。
- 認証導入後は 403（CSRF トークン不正など）が利用者に見える場面が増える。
- 対応案: 最低限 `templates/error/403.html` を用意する。

## 5. 将来フェーズの課題

### L-10 新規登録（サインアップ）画面がない

- ログイン画面に「新規登録」リンクがあるが遷移先がない（`chasing_cats.html:171`、`href="#"`）。
- 第 1 フェーズではリンクを非表示にする。
- 検討事項: 誰でも登録できるようにするか、管理者だけがユーザを追加できるようにするか。
  `username`（50 文字、UNIQUE）の入力ルール、パスワードの強度ルール、メールアドレスの実在確認。

### L-11 パスワード再設定の手段がない

- パスワードを忘れた利用者を救済できない。当面は DB を直接更新するしかない。
- メール送信の仕組みがアプリにないため、通知機能（バッチ設計書でも将来対応扱い）と合わせて検討する。

### L-12 設定画面のアカウント情報・パスワード変更がモック

- `settings.html` のアカウント情報は固定値（`:49-62`）、保存ボタンはトースト表示のみ（`settings.js:5-17`）。
- `SettingsController` は画面を返すだけで、ログインユーザの情報を渡していない。
- ログイン機能ができると「表示されている名前が自分と違う」状態になるため、
  第 1 フェーズでも表示だけはログインユーザの値に差し替えることを推奨する。
- `users.preferred_currency_id` と設定画面の「既定の表示通貨」は対応するはずだが、つながっていない。

### L-13 ロール（権限）の概念がない

- `users` にロールを表すカラムがない。第 1 フェーズではログインした全員が全操作を実行できる。
- 権限を分けたくなる操作: バッチ手動実行（外部 API を消費する）、マスタの登録・更新・削除、評価モデルの編集。
- 対応案: `users.role varchar(20) not null default 'USER'` を追加し、`/rest_market_data_sync/**` などを管理者限定にする。

### L-14 ログイン試行回数の制限がない

- パスワードの総当たりを防ぐ仕組みがない。
- 対応案: `users` に `failed_login_count`、`locked_until` を追加し、一定回数の失敗で一時ロックする。
  ローカル利用のみの間は優先度を下げてよい。

### L-15 ログイン状態の保持（Remember-me）がない

- ブラウザを閉じる、またはアプリを再起動するたびに再ログインが必要になる。
- 開発中は devtools の再起動でもセッションが消える。支障が大きければ検討する。

### L-16 ユーザごとのデータ分離ができていない

- 銘柄詳細のパラメータ保存（`POST /rest_stock_detail/{code}/parameter-defaults`）は
  `company_valuation_parameter_defaults` を更新する。これは全ユーザ共通の値である。
  複数人で使うと、他人の変更で自分の前提値が変わる。
- `user_simulations.user_id`、`user_valuation_parameters.user_id` というユーザ別の受け皿は DB にあるが、
  アプリからは使われていない。
- `StockDetailServiceImpl` には DTO をシングルトンで持つことに起因する既知の不具合があり、
  複数ユーザの同時利用で他社・他人のデータが混ざるおそれがある。同時利用が始まる前に解消が必要。
- 対応案: ログインユーザの ID は `LoginUser.id` で取れるようにしておく（設計書 5.3）。
  データ分離そのものは別設計とする。
